## Verified browser acceptance flow

1. Administrator creates instructor and student accounts through the UI.
2. Instructor creates a course, section, lesson, question, quiz and assignment, submits for review and publishes.
3. Student enrolls and completes a lesson; the displayed progress reflects the server's saved record.
4. Student answers and submits a quiz and sees the released result.
5. Student submits an assignment; instructor grades and releases feedback.
6. Student views the actual marks and feedback, becomes eligible and issues a certificate.
7. Student accesses the certificate area and is blocked from the people-management route.
8. A second browser test renders real dashboard data and exercises mobile navigation/catalog layout.

These browser tests use isolated temporary databases and development accounts. No core UI is backed by fake application responses. Component tests mock network boundaries to isolate UI behavior; API and browser tests exercise real services and persisted records.

## Backend coverage of business/security boundaries

The 18 test cases include many individual HTTP/assertion checks: tenant isolation and ID guessing, protected files, privilege assignment, read-only roles, delegated TA grading, session revocation/CSRF/rotation/replay, one-use password reset, password policy and account lockout, MFA enrollment/code reuse, academic CRUD/reference integrity/cohort membership, CSV preview/atomic import, course publication/revisions, thumbnail visibility/copy, enrollment capacity/waitlists, prerequisite/drip rules, idempotent progress, quiz timing/attempt limits/key hiding/negative and manual marking, rubric totals/submission versions/deadlines/release, certificate eligibility/revocation/reissue, attendance corrections, notifications/discussions/messages, real report counts, outbox unconfigured/retry behavior and reminder deduplication.

## Bounded limitations and integration status

- Local file storage is implemented; managed object storage, antivirus/quarantine, external meeting provisioning and plagiarism providers require real adapters/configuration. Manual meeting URLs are supported; no external meeting or plagiarism result is simulated.
- CSV user imports are limited to 500 rows and report exports to 10,000 records; use reviewed batches/date windows. Relationship pickers and assessment panels load at most 100 records even though their APIs paginate.
- Roles are explicit fixed mappings; the UI manages assignments and displays permissions. There is no arbitrary custom-role policy editor or per-report auditor grant editor.
- Some general administrative response entries use flexible record maps; exhaustive response DTOs/generated frontend clients are a further hardening task. Sensitive fields and learner answer keys are filtered server-side and tested.
- Certificate templates support text/issuer/branding configuration, not a visual template designer. The bundled PDF base font needs replacement with a tested licensed Unicode font for non-Latin glyph coverage.
- The profile timezone is stored, while dates currently display in the browser's locale/timezone. TOTP backup recovery codes are not implemented; recovery requires an operator-reviewed process.
- Course tags are a bounded JSON list, levels are program attributes, course offerings represent class groups, and enrollment status represents requests/waitlists; these are deliberate shared-domain modeling choices.
- No SCORM/LTI/xAPI, rich HTML lesson editor, external video transcoding or unchecked automatic populated SQLite-to-PostgreSQL data copier is included.
- One scheduler and local persistent storage are the supported deployment design. Replication/load capacity and independent approval-only publishing policies need institution-specific review.
